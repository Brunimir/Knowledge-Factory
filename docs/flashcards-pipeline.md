# Generate-Flashcards Pipeline

This file contains the full PHASE GF-0 → GF-4 definitions for the
`generate-flashcards` command. CLAUDE.md references this file rather than
embedding the content, so the agent only loads it when the user actually
invokes generate-flashcards. Do NOT load it for any other command.

The general gates that apply to generate-flashcards (FINAL CRITERIA GATE,
SAFETY RULES, WINDOWS FILE OPERATION PATTERNS) remain in CLAUDE.md — only
the long phase definitions are here.

---

# DESIGN

Output is per-MOC per batch. The first run for an MOC writes
Flashcards_{moc_stem}.md; every subsequent run writes a NEW file named
"Flashcards_{moc_stem} - Batch {N}.md" (N = 2, 3, ...). Never append to,
rewrite, or reorder cards in a previously written flashcard file. The
flashcards-obsidian plugin inserts <!--ID:nnn--> markers after each card on
first Anki sync; appending to a file that has already been synced (or that
the plugin thinks it has synced) triggers the AnkiConnect silent-fail
duplicate trap, which leaves new cards out of Anki without surfacing an
error. One file per batch isolates each sync. Folder-based deck routing
keeps every batch file in the same Anki sub-deck regardless of filename.

Cards use the inline format with the :: separator (matches the plugin's
inlineSeparator setting). One idea per card, about 9 words on the back and 18
at most, worded from what the note says, up to 6 cards per concept. Existing cards are never rewritten.

────────────────────────────────────────────────────────────────
PHASE GF-0 — IDENTIFY CANDIDATES (the manifest is the sole input)

  Do NOT read VAULT_INDEX.json. The agent's only input is the
  pre-extracted manifest FLASHCARD_CANDIDATES.json (loaded in GF-1),
  which already contains exactly the eligible candidates. Reading the
  full index here would duplicate the eligibility filter and is the
  single largest avoidable read of the run. Flashcard card bodies
  contain no wikilinks, so VALID_NOTES is not needed anywhere in this
  pipeline.

  ELIGIBILITY — defined here, once, for the whole pipeline:
    A note is eligible when
        status     == "final"   AND
        flashcards == false
    Both flags are required. status:final = the human has read it through,
    approved it, and the note structure is locked; flashcards:false = no
    card has been generated yet.
    Any note missing one of the two is not eligible. The extractor
    (extract_flashcard_candidates.ps1) enforces this filter when building
    the manifest, and the launcher refuses to start the agent when the
    manifest is empty — so the agent never has to recompute it.

  If the manifest is empty (no eligible candidates):
    Print: "No final notes need flashcards - nothing to process."
    Stop.

  Print: "Generating flashcards for {N} concept(s) across {M} MOCs."
  (N and M are derived from the manifest, not from the index.)

────────────────────────────────────────────────────────────────
PHASE GF-1 — LOAD CANDIDATE MANIFEST (one file read, not N)

  Read the pre-extracted manifest:
    00_Inbox\FLASHCARD_CANDIDATES.json

  This file is generated by extract_flashcard_candidates.ps1 (run by
  the launch script before the agent starts). It contains every
  eligible candidate with these fields already parsed:

    stem          - filename stem (no .md)
    title         - frontmatter title
    moc_stem      - first entry in moc: list
    humanized_moc - "Learning and Memory" form (for the file header)
    description   - frontmatter description
    core          - lead prose of ## Core Idea (Summary), without the
                    **Metaphor:**/**Example:** sub-blocks
    metaphor      - extracted **Metaphor:** value, multi-line capable,
                    or null if not present (do NOT invent one)
    mechanism     - full ## Mechanism (Key details) section text
                    (includes bullets and the boundary line - the
                    boundary is also provided separately)
    boundary      - extracted **Boundary condition:** value, or null
    when_to       - extracted **When to use:** value, or null
                    (legacy fallback to **Strengths:** applied)
    when_not      - extracted **When NOT to use:** value, or null
                    (legacy fallback to **Opportunities:** /
                    **Limitations:** applied)
    is_stub       - true if the note appears to be a navigation stub
                    (core says "has been split into", description
                    matches /stub/, etc.) - see STUB HANDLING below
    stub_reason   - human-readable reason the note was flagged
    has_required  - true if the minimum required fields are present:
                    title AND moc_stem AND core AND
                    (when_to OR when_not)

  DO NOT open the source .md files. Reading from the manifest is the
  entire point - it cuts ~50% of extraction-phase tokens by avoiding
  N round trips.

  If the manifest is missing or its `generated` date is not today,
  run the extraction script first:
    powershell -ExecutionPolicy Bypass -File `
      "$env:VAULT_ROOT\extract_flashcard_candidates.ps1"
  Then read the freshly written manifest.

  STUB HANDLING (non-interactive — resolved at launch):
    Stubs are decided ONCE by the launcher, which prompts the human (or
    takes -IncludeStubs) and records the answer in the manifest's
    TOP-LEVEL `include_stubs` boolean (sibling of `candidates`, `generated`).
    The agent obeys it silently:
      • manifest.include_stubs == true  → generate cards for is_stub
                                          candidates too.
      • otherwise                        → skip every is_stub candidate, log:
                                          "ⓘ {stem}: skipped (flagged stub)."
    Do NOT stop and ask the user about stubs mid-run.

  REQUIRED-FIELDS GATE (silent):
    For every candidate where has_required == false, log:
      "⚠ {stem}: missing {fields} - skipping."
    and skip. Do not write partial cards.

  TRUTHFULNESS:
    Safety Rule #7 (CLAUDE.md) applies in full to all card generation —
    never invent facts, metaphors, boundaries, or examples; if a manifest
    field is null, omit that part of the card or skip the item. Do not
    restate the rule; it governs every line written below.

────────────────────────────────────────────────────────────────
PHASE GF-2 — GROUP BY MOC AND WRITE BATCH FILE

  Target folder : 20_Learning\23_FlashCards\
  Target file   : a NEW file per run, named by batch number:
                    Batch 1  → Flashcards_{moc_stem}.md
                    Batch N (N≥2) → "Flashcards_{moc_stem} - Batch {N}.md"

  Determine N before writing:
    base = "Flashcards_{moc_stem}.md"
    pattern = "Flashcards_{moc_stem} - Batch *.md"
    If neither base nor any pattern match exists → N = 1, file = base
    Else N = (highest existing batch number for this MOC) + 1, where
      base counts as batch 1 and each "- Batch K.md" contributes K.
      File = "Flashcards_{moc_stem} - Batch {N}.md".
    Never overwrite an existing flashcard file. If the chosen filename
    already exists, abort with an error - do not silently bump N
    further, as that hides a prior failed run.

  Group successfully-extracted candidates by moc_stem.

  For each MOC group:

    Create the batch file fresh with this header (and a single blank
    line, no cards yet). The title carries the batch suffix only when
    N ≥ 2; for batch 1 the title is plain "Flashcards - {humanized moc_stem}".

        ---
        title: Flashcards - {humanized moc_stem}
        type: flashcard-batch
        moc: [{moc_stem}]
        created: {today}
        tags:
          - card
        ---

        # Flashcards - {humanized moc_stem}


      Where humanized moc_stem strips the leading "MOC_" and replaces
      underscores with spaces. Example: MOC_Learning_and_Memory →
      "Learning and Memory".

    For each candidate in this group, write adaptive card blocks
    after the header (in encounter order). Each card is structured as:
      one list-item line, `- Question :: Answer` (flashcards-obsidian
      v2 syntax), then a blank line before the next card. There is NO
      `#card` line: v2 reads a standalone `#card` as "the previous
      heading is the question", so the card would sync with the file
      title as its front. Never write a `^id` anchor - the plugin adds it.

    One card per idea the note treats as central, up to 6 per concept:
    its core mechanism, its boundary condition, its practical consequence.
    Empty manifest fields yield no card. A concept's use and avoid cases are
    separate ideas, so they take separate cards.

  Question rules:
    - NAME THE CONCEPT in every question, bare and without quotes. It gives
      the card its context when reviewed alone, and GATE-KF-05 assigns a card
      to its note by finding at least 60% of the title's content words in the
      question: a question that does not name it is refused (FC-3).
    - Precise: only one answer fits, and it comes out the same each review.
    - The question must not contain or give away the answer. Avoid either/or
      questions, which test recognition rather than recall.
    - Never refer to the document ("in the note's picture").
    - The question is under the same FIDELITY rule as the answer: it states
      and implies nothing the note does not say.
    - Shape it to the idea (cause, contrast, consequence, when, when not)
      rather than a fixed template.

  Card body rules:
    - ONE IDEA per card: one independently forgettable assertion,
      something the reviewer could get right or wrong on its own.
      Elaborations of the SAME assertion count once.
    - SHORT: 9 words or fewer on the back, one sentence or a fragment. Go
      over 9 only when the idea cannot be said shorter and stay true. No
      semicolons, and no second clause adding another idea. GATE-KF-05
      refuses a back over 18 and warns over 9, on a second sentence or on
      a semicolon.
    - WORDED TO STICK, FROM THE NOTE: use the note's metaphor, its concrete
      example or its own vivid phrase where it has one. Where it has none,
      write a plain card. Never invent an image, example or analogy.
    - A QUALIFIER IS NEVER DROPPED TO SAVE WORDS. If a card cannot hold it,
      split the card or leave that idea out.
    - ACRONYMS, on the question and the answer: write each one with its
      spelled-out form in brackets, every time: ISS (International Space
      Station). The whole form counts as ONE word. The spelled-out form
      comes from the note. If the note does not spell it out, keep the
      acronym as the note writes it and name it in your final report.
    - Anything left out stays in the concept note, which remains the
      reference document.
    - Plain text. NO markdown bold labels, bullets, headings or wikilinks.
    - Replace em-dashes (—) with " - " (space hyphen space).
    - FIDELITY (Safety Rule #7, absolute): every clause on a card must
      trace to a specific sentence or bullet in the source note.
      Permitted: compress, reorder, re-syntax, de-link, split, omit.
      FORBIDDEN: adding any fact/example/metaphor/number not in the
      note; strengthening or weakening a claim (can -> does, often ->
      always, suggests -> proves); dropping a scope qualifier so a
      bounded claim reads as universal; inferring a consequence the
      note does not state; importing content from another note or
      from your own knowledge. If a clause cannot be pointed back to
      the note, DELETE it; if that empties the card, do not emit it.
      An empty manifest field yields NO card - never fill a gap.

  Reference example - Saving String (Prose Mechanics MOC). One idea per card,
  each worded from the note, with the concept named in every question:

    - What is the compost heap picture of Saving String? :: Scraps sit
    until they become rich soil nourishing a large harvest.
    - In Saving String, what does declaring an interest create? :: A
    subconscious search mechanism flagging relevant environmental stimuli.
    - In Saving String, what does collecting without producing become
    without a harvest phase? :: Information hoarding.
    - For what kind of work is Saving String not useful? :: Tight-deadline
    work, where collection time does not exist.

  (Shown wrapped here. On disk each card is one continuous line.)

  Minimum 1 card per concept. MAXIMUM 6, and 6 is a ceiling, not a target:
  stop when the ideas the note treats as central run out. Fewer true cards
  beat more.

  WRITE DISCIPLINE — critical for Anki ID stability:
    0. Validate frontmatter before writing — ACTUALLY PARSE IT, do not
       eyeball it. A flashcard file with malformed frontmatter (missing
       opening ---, a wrapped value, an unquoted interior ": ") is
       SILENTLY DROPPED by generate_index.py (no error), and once the
       plugin syncs it and writes <!--ID--> markers the file is immutable
       — you cannot fix it later. So gate it now: write the candidate to
       a temp file and run the indexer's own parser:
         $tmp = Join-Path $env:TEMP "pkm_fm_check.md"
         Set-Content -Path $tmp -Value $fileContent -Encoding UTF8
         python -c "import sys; sys.path.insert(0, r'$env:VAULT_ROOT'); from generate_index import parse_frontmatter; c=open(sys.argv[1], encoding='utf-8').read(); f,e=parse_frontmatter(c); assert f, (e[0] if e else 'no frontmatter — would be SILENTLY DROPPED (missing opening --- ?)'); print('FM_OK')" $tmp
       Must print FM_OK before the real write. Fix and re-run on failure.
    1. Always create a NEW file with Set-Content -Encoding UTF8.
       Never read, append to, or rewrite a pre-existing flashcard
       file - not even to "fix" formatting.
    2. Confirm the chosen filename does not already exist before
       writing (Test-Path). If it does, abort with an error.
    3. Once the plugin syncs the file and writes back <!--ID:nnn-->
       markers, treat that file as immutable. The next generation
       run produces a separate batch file.

  Track every filename you write this run — GF-4 must list them all in
  files_written[] so the launcher syncs the right files.

  GF-2 INTERIM SUMMARY — after writing this batch, print ONLY the
  one-line totals (the full per-row table is produced once, in GF-4,
  to avoid two near-identical tables per run):
    "Generated: X concepts (Y cards) | Skipped: Z | MOC files touched: M"

────────────────────────────────────────────────────────────────
PHASE GF-3 — PATCH SOURCE NOTES  (flashcards: false → true)

  For each candidate whose cards were successfully written this run:
    Patch 20_Learning\21_Concepts\{stem}.md:
      $content = $content -replace 'flashcards: false', 'flashcards: true'
      $content = $content -replace 'updated: \d{4}-\d{2}-\d{2}', "updated: $today"

  Patch only sources whose cards were actually written this run.
  Never patch a source that was skipped. (Sync verification — whether
  Anki actually ingested the cards — is performed by the launcher after
  the agent returns; see GF-4 files_written[] and the launcher's
  sync_verification output.)

────────────────────────────────────────────────────────────────
PHASE GF-4 — REPORT

  Two outputs: a markdown table in the agent transcript (for log
  history) and a JSON results file the launch script renders as a
  console-aligned table (for at-a-glance terminal review). This is the
  ONLY full per-row table in the run.

  (a) MARKDOWN TABLE — print to the transcript, with post-patch status:
      | MOC | Concept | What | How | When | Status & comment |

  Column rules:
    MOC      — humanized MOC name (e.g. "Learning and Memory")
    Concept  — concept stem (e.g. "Active_Recall")
    What     — ✓ written | — skipped | ⚠ flagged
    How      — ✓ written | — skipped | ⚠ flagged  (— if mechanism null)
    When     — ✓ written | — skipped | ⚠ flagged  (— if when_to & when_not null)
    Status   — final state after GF-3, e.g.:
      "All 3 cards written, source patched"
      "2/3 cards written, source patched - HOW skipped (no mechanism)"
      "Skipped - missing required fields (source NOT patched)"
      "Skipped - stub, launcher declined (source NOT patched)"
      "Cards written but source patch FAILED - manual review required"

  One row per ELIGIBLE candidate (from GF-1), including skipped ones.
  Group rows by MOC. After the table, print one totals line:
    "Generated: X concepts (Y cards) | Sources patched: P |
     Skipped: Z | MOC files touched: M"

  (b) JSON RESULTS FILE — write to:
      00_Inbox/FLASHCARD_RUN_RESULT.json

  Schema:
    {
      "generated": "YYYY-MM-DD",
      "files_written": [
        "Flashcards_Learning_and_Memory.md",
        "Flashcards_Biology_of_Performance - Batch 2.md"
      ],
      "rows": [
        {
          "moc":     "Learning and Memory",
          "concept": "Active_Recall",
          "what":    "✓",   // ✓ written | — skipped | ⚠ flagged
          "how":     "✓",
          "when":    "✓",
          "status":  "All 3 cards written, source patched"
        },
        ...
      ],
      "totals": {
        "concepts_generated":  N,
        "cards_total":         3*N approx (3 max per note, fewer if a
                               type's source field was empty),
        "sources_patched":     P,
        "skipped":             Z,
        "moc_files_touched":   M
      }
    }

  files_written[] — REQUIRED. The exact filename (leaf, including any
  " - Batch N" suffix) of every flashcard file this run actually wrote.
  The launch script syncs from THIS list, not a guessed batch-1 name, so
  that batch ≥ 2 files are synced correctly. The launcher then appends a
  `sync_verification` array (file → synced bool, by checking for Anki ID
  markers) after syncing — do not write that field yourself.

  Sort `rows` by moc then concept. Use UTF-8 encoding (no BOM).
  The launch script reads this and renders a console-aligned table
  after Claude returns.

  DO NOT re-output card content - it is already in the flashcard files.

────────────────────────────────────────────────────────────────
FLASHCARD FORMAT NOTES (flashcards-obsidian plugin)
  - Each card is one list-item line:
        - Question? :: Answer text.
    The plugin (v2) parses a list item containing :: as a card, with
    front/back split on the :: separator. A standalone "#card" line
    must NOT be used - v2 treats it as "previous heading is the
    question".
  - inlineSeparator is :: (configured in plugin data.json).
  - The "card" hashtag (hashtag.basicTag in plugin data.json) is not
    used by list-item cards; the legacy flashcardsTag key is unused.
  - The deck comes from the file's card-deck: frontmatter line (the
    generator writes it); folderBasedDecks is ON in data.json as the
    fallback for files without one.
  - On first sync the plugin appends a block anchor (^q-xxxx in v2;
    legacy 13-digit ^NNNNNNNNNNNNN ids are still accepted) at the END
    of the card line, and records the Anki note id under flashcards:
    in the frontmatter. On re-sync it matches by ID, updating Anki
    when the markdown changes. NEVER edit, reorder, or remove these
    IDs or their cards become orphaned.
  - SILENT-FAIL TRAP: AnkiConnect rejects "duplicates" (notes whose
    front field matches an existing card in any deck under the same
    note model). When this happens the plugin shows ONLY "Nothing to
    do, everything is up to date" - the duplicate errors appear in
    the dev console (Ctrl+Shift+I), not the UI. If sync produces no
    IDs in the file after a successful-looking run, check the
    console for "cannot create note because it is a duplicate" and
    delete the orphan Anki cards via Browse before re-syncing.
    (The launcher now performs this ID check automatically and warns
    loudly when a just-written file has zero Anki IDs.)
